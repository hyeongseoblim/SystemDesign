# 콘텐츠 확장 설계

## 1. 목적과 현재 기준선

이 문서는 학습 카드 수를 늘리되 같은 주제를 반복 생성하거나, 카드 품질이 낮아지는 문제를 막기 위한 운영 설계다. 숫자는 **소스 저장소 기준 2026-08-29**이며, 실제 배포 DB의 발행 수와는 다를 수 있다.

| 항목 | 현재 | 의미 |
|---|---:|---|
| 수동 발행 카드 | 129개 | `apps/api/src/main/resources/content/*.md`의 프론트매터가 정상일 때 `ContentSeeder`가 적재하는 수 |
| 수동 카드 영역 | 8개 | 시스템 디자인, 물류, 백엔드 개발·아키텍처, 데이터베이스, 인프라, CS, AI/LLM |
| AI 생성 대기 주제 | 314개 | 마이그레이션이 만든 369개 중 수동 카드가 해결한 55개를 제외한 신규 DB 부팅 완료 기준 |
| AI 자동 생성 | 기본 비활성 | Cloud Run scale-to-zero 환경에서 Cloud Scheduler 없이 실행하면 누락·비용 통제가 어려움 |

현재 수동 카드는 시스템 디자인 26개, 물류 19개, AI·데이터베이스·백엔드 아키텍처·백엔드 개발 각 15개, 인프라 13개, CS 11개다. 모드는 CONCEPT 80개, DESIGN 27개, INTERVIEW 17개, REVIEW 5개다.

### AI/LLM 확장: 15개

기초 원리부터 프로덕션 설계까지 `Transformer·Context → Prompt·Embedding → RAG → Tool/MCP·Agent → 평가·보안 → 추론 서빙·Fine-tuning·Multimodal → 면접·코드 리뷰` 순서로 구성했다. 버전 변화가 빠른 제품 기능보다 오래 유지되는 원리와 운영 경계를 우선하며, 최신성이 필요한 내용은 논문·표준·공식 문서를 카드에 연결한다.

## 4. 중복 방지 모델

### 문제

현재 `curriculum_topics`에는 제목, 영역, 모드, `generated` Boolean만 있다. 수동 카드가 나중에 같은 주제를 다뤄도 커리큘럼 항목과 연결되지 않으므로 AI 생성 후보로 남는다. 또한 `generated=true`는 초안(DRAFT)과 발행(PUBLISHED)을 구분하지 못한다.

### 목표 모델

다음 스키마 변경을 카드 대량 작성 전에 적용한다. 기존 `generated`와 `generated_card_id`는 호환 기간 동안 유지하고, 새 상태가 기준값이 된다.

| 필드 | 예시 | 용도 |
|---|---|---|
| `topic_key` | `system-design-101` | 제목이 아니라 마이그레이션에서 고정한 전역 고유 키. 커리큘럼·수동 카드·AI 카드를 연결 |
| `resolution_status` | `PENDING`, `MANUAL`, `AI_DRAFT`, `AI_PUBLISHED`, `SKIPPED` | 주제의 실제 처리 상태 |
| `resolved_card_id` | 카드 UUID | 주제를 해결한 카드. 수동·AI 모두 연결 가능 |
| `supersedes_topic_key` | 선택값 | 더 넓은 카드가 기존 주제를 대체했을 때 추적 |

V6 마이그레이션과 애플리케이션 연동은 구현됐다. 전환·운영 절차는 다음과 같다.

1. Flyway V6가 위 필드와 제약을 추가한다. 기존 주제는 `<area>-<display_order 3자리>` 키로 한 번 고정하며, 이후 순서를 바꿔도 키를 변경하지 않는다.
2. 생성 쿼리는 `resolution_status=PENDING`만 선택한다. AI 품질 미달이면 `AI_DRAFT`, 통과하면 `AI_PUBLISHED`로 기록한다.
3. 수동 시더는 선택적인 `topicKey` 프론트매터를 읽고, 카드 생성 뒤 커리큘럼 주제를 `MANUAL`로 같은 트랜잭션에서 해결한다. 기존 slug를 만나도 누락된 연결을 보강하며, 키가 없으면 기존처럼 카드만 적재한다.
4. 기존 59개와 V2·V4를 대조한 결과, V3에서 제거한 7개 외에는 완전히 같은 범위의 주제가 없었다. 기존 종합 카드를 더 좁고 깊게 파고드는 항목은 대기 상태로 유지한다.

이 모델을 적용하기 전에는 새 수동 카드의 제목을 V4 목록과 수동 대조하고, 대응 주제를 AI 후보에서 제외하는 마이그레이션을 함께 작성한다.

## 5. 카드 제작·검수 흐름

```
커리큘럼 백로그 선정
        ↓
카드 명세(topic_key·난이도·모드·핵심 질문) 작성
        ↓
Markdown 카드 작성 → 정적 린트 → 로컬 시드
        ↓                         ↓
커리큘럼 상태 해결 ← 내용·Mermaid·모바일 화면 검수
        ↓
발행 및 다음 배치 선정
```

### 정적 린트

`scripts/check-content.sh`를 추가해 PR과 로컬에서 다음을 검사한다.

- slug와 `topicKey`의 중복, 필수 프론트매터, 영역·모드 enum, 난이도 1~5
- 질문 정확히 3개, 태그 2~6개, 제목·요약·본문의 공백 여부
- Mermaid 코드펜스 1개 이상, 비교 표 1개 이상, callout 1개 이상, 언어 지정 코드블록 1개 이상
- 링크 형식, 깨진 내부 링크, frontmatter YAML 파싱
- 커리큘럼 항목을 해결하는 수동 카드에 `topicKey`가 있는지

구조·메타데이터 계약은 전체 카드에 강제한다. 기존 33개 카드의 언어 지정 코드블록 부채를 정리했으며, 이제 Mermaid 외 코드블록 누락도 검사 실패로 처리한다.

### 사람 검수 기준

- **사실성**: 버전 의존 기술은 공식 문서 또는 신뢰할 수 있는 1차 출처 링크를 카드 끝에 둔다.
- **학습성**: 정의만 나열하지 않고 문제 상황, 트레이드오프, 면접 질문 3개를 제공한다.
- **실행 가능성**: 숫자·용량·장애 시나리오는 가정을 명시하고, 물류 사례는 보편적 원리와 특정 기업 사실을 구분한다.
- **표현 품질**: 모바일 화면에서 표가 과도하게 넓지 않은지, Mermaid가 실제 렌더되는지 확인한다.

## 8. 기존 콘텐츠 보강 기록

2026-09-12~13에는 카드 수를 늘리기보다 기존 129개 구조 점검과 32개 본문 수정(27개 심층 보강·5개 부분 정정)을 진행했다. 질문별 점검 해설은 34개 카드/102문항으로 확대했다. 상세 근거·카드별 상태·후속 순서는 [기존 콘텐츠 점검표](content-audit-2026-09-12.md)에 기록한다. 기존 DB 반영에는 V9와 Web 해설 배포가 필요하며, 이 기록 시점에는 운영 반영 전이다.

후속 검수로 Kubernetes 스토리지 1개를 추가해 누적 33개 본문(28개 심층·5개 부분), 해설 35개/105문항이다. 후속 본문은 V10으로 분리했다.

V9 배치 32개 본문과 34개 해설은 2026-09-13에 운영 반영했다. [배포 기록](deployment-2026-09-13.md)에 검증 근거와 미배포 후속 V10을 구분했다.

Kubernetes 네트워킹·장애 면접도 추가 검수해 누적 본문 35개(심층 30개·부분 5개), 해설 37개/111문항이다. V10은 스토리지를 포함한 세 카드다.
